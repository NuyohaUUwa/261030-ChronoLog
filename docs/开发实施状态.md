# 开发实施状态

更新：2026-11-07。本表是整体任务／功能进度的唯一入口，覆盖 [产品规划](系统设计蓝图.md)。

> [!NOTE]
> **产品定位与执行原则（2026-11-07 用户明确）**：
> 1. **个人工具定位**：本项目目前作为个人工具类产品开发，非标准工业级产品。全面精简和降低现有规划的验收与审查条件。
> 2. **执行优先级**：后续开发全过程严格遵循 **功能 > 性能 > 审查 > 交互** 的优先级执行。
> 3. **极简务实门禁**：废除重量级独立审查矩阵、长篇 Review 报告及边缘故障注入演练；验证以“核心功能跑通并可用”为主，通过基础测试/构建即可，发现问题就地修复，不以形式化审查或次要交互细节阻塞交付。
> 4. **阶段推进顺序**：严格按照 **阶段一：服务端功能和接口开发（优先） -> 阶段二：Web 端使用和页面优化 -> 阶段三：安卓移动端开发** 顺序推进。各阶段具备独立可用成果，不跳步倒置。
> 5. **防范围膨胀准则（PT-01 落实）**：各阶段严格划定【核心闭环】与【候选增强】界限。各阶段仅以【核心闭环】通过为准出条件；所有【候选增强】项必须**等待用户明确指示后再行启动补齐**，严禁擅自提前开发或作为前置依赖阻塞主流程。

## 状态与维护规则

| 状态 | 判定 |
|---|---|
| 已完成 | 表中限定范围已有实现和对应验证记录；不扩展为整个模块或线上效果已验收 |
| 开发中 | 已实际开始实现／联调，须写明执行人、下一步、阻塞及最近更新；仅有计划不算 |
| 待开发 | 未实现的功能或独立交付任务；有依赖的任务注明前置条件 |
| 待优化 | 已有基础能力，但质量、可靠性、体验或验证仍需补齐；不代表可忽略 |

执行任务的人负责同步维护：开始工作时移动到开发中；验收后移动到已完成并记录证据；暂停则保留实际进展并注明阻塞。用稳定编号移动原行，不复制两份互相矛盾的状态。拆分任务时保留原编号关联，发现回归可重新打开。

每次功能、配置或交付变更，结束前检查本表及 README 中的文档职责表，同步相关契约／操作指南；没有变化的文档无需机械改日期。文档完成只能关闭文档任务，不能关闭实现或验收任务。原始报告／截图放忽略的 reviews/，Git 保留结论、限制、测试代码与可维护的进度。上线记录须另记源码提交、产物提交、时间及结果，不能仅凭构建通过标为已上线。
